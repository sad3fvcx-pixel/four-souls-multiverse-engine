# 2. Продуктовая идея

> FSME — это не движок конкретного дополнения, а универсальный симулятор правил
> The Binding of Isaac: Four Souls, способный работать с оригинальными картами
> и пользовательским контентом через систему данных и DSL.

Из этого следуют четыре продуктовых требования:

| Требование | Что означает практически |
|---|---|
| Универсальность | Движок не знает ни одной конкретной карты по имени |
| Расширяемость | Новая карта = новый файл данных, а не новый код |
| Детерминизм | Один и тот же seed + один и тот же ввод = одна и та же партия |
| Проверяемость | Любая партия воспроизводима и покрывается автотестом |

`Syndrome of the Multiverse` — первый потребитель этих возможностей, но не
привилегированный: оригинальный набор и кастомные наборы проходят через один
и тот же content pipeline.

# 3. Структура репозитория

```
four-souls-multiverse-engine/
├── docs/                 # Документация архитектуры
├── spec/                 # Спецификации правил игры
├── tests/                # Автотесты
├── tools/                # Вспомогательные инструменты
├── examples/             # Примеры карт и сценариев
├── content/              # Игровой контент
└── src/
    └── fsme/
```

Разделение принципиальное: `src/` содержит механики, `content/` содержит карты.
Изменение `content/` никогда не требует изменения `src/`, пока используемые
механики уже поддержаны.

# 5. Слои и направление зависимостей

Список модулей не задаёт порядок сборки — его задают зависимости.
Зависимости разрешены **только сверху вниз**.

```
Слой 4   game                        управление партией
              ↓
Слой 3   runtime, rules              исполнение правил
              ↓
Слой 2   commands, stack,            доменные определения
         effects, abilities, cards
              ↓
Слой 1   state, events               данные и транспорт
              ↓
Слой 0   util, rng, config,          инфраструктура
         logging
```

Сквозные модули (`validation`, `serialization`, `replay`, `content`,
`database`, `plugins`) зависят от нижних слоёв и не зависят друг от друга.

Жёсткие правила:

1. `state` не импортирует ничего, кроме `util`.
2. `state` ничего не исполняет — он только хранит данные.
3. Мутировать `GameState` имеет право **только** `runtime`.
4. `cards` — данные; логика карт не живёт в `cards`.
5. Обратные импорты (снизу вверх) запрещены; при необходимости используется событие.

Правило 3 — центральное. Оно превращает «Event Driven» и «Deterministic» из
намерения в проверяемое свойство: точка мутации одна, значит и точка записи
в replay-лог одна.

# 8. Card Maker

Отдельный инструмент, не часть движка:

```
tools/
└── card_editor/
```

Сценарий использования:

1. пользователь выбирает тип карты;
2. выбирает триггер;
3. добавляет эффекты;
4. сохраняет JSON;
5. движок автоматически проверяет карту.

Card Maker обязан использовать тот же `validation/`, что и движок —
второй реализации проверки быть не должно.

# 9. Этапы разработки

Каждый этап считается завершённым только по критерию выхода.
Общий Definition of Done из `DEVELOPMENT_GUIDELINES.md` применяется к каждому.

## Этап 1 — Фундамент

Состав: структура проекта, Runtime, State, Events, Stack.

Критерий выхода:
- `runtime/` существует и владеет единственной точкой мутации `GameState`;
- событие проходит путь `emit → listener → stack → resolve` в тесте;
- `tests/` запускается и зелёный.

## Этап 2 — Выполнение правил

Состав: Commands, Effects, Ability Resolver, DSL.

Критерий выхода:
- команда валидируется, исполняется и порождает события;
- способность, описанная в DSL, разрешается без кода под конкретную карту;
- реестры эффектов/триггеров/условий подключены к Runtime.

## Этап 3 — Первая рабочая партия

Цель — запустить сквозной сценарий:

```
Start Game
     ↓
Player Turn
     ↓
Attack
     ↓
Resolve Effect
     ↓
End Turn
```

Критерий выхода:
- партия из нескольких ходов доходит до конца без ручного вмешательства;
- один и тот же seed даёт побайтово одинаковый лог партии.

## Этап 4 — Официальный контент

Состав: оригинальные карты, монстры, предметы, персонажи.

Критерий выхода:
- `OFFICIAL_CARD_COVERAGE.md` отражает фактическое покрытие;
- каждая нереализованная карта имеет причину: отсутствующая механика, а не «нет кода».

## Этап 5 — Редактор карт

Состав: Card Maker, проверка карт, экспорт, импорт.

Критерий выхода:
- карта, созданная в редакторе, загружается движком без правок вручную.

## Этап 6 — Расширения

Состав: моды, пользовательские наборы, онлайн, ИИ-игроки, симуляции баланса.

Критерий выхода определяется отдельно при входе в этап.

# 11. Расхождения между планом и репозиторием

Фиксируются явно, чтобы этап 1 начинался с известной точки.

## 11.1 Отсутствует

- `src/fsme/runtime/` — ядро, вокруг которого строится всё остальное;
- `src/fsme/abilities/` — DSL способностей;
- `src/fsme/rules/` — правила Four Souls;
- `src/fsme/replay/` — повторы (при том, что `REPLAY_SYSTEM.md` уже написан);
- `tests/`, `tools/`, `examples/`, `content/` — все четыре каталога верхнего уровня.

Отсутствие `tests/` — прямое нарушение принципа «Test First» и Definition of Done.
`pyproject.toml` уже указывает `testpaths = ["tests"]`, то есть конфигурация ждёт
каталог, которого нет.

## 11.2 Лишнее относительно плана

`src/fsme/resources/` (646 строк) в плане не предусмотрен и пересекается по смыслу
с `content/` и `database/`. Требуется решение: слить в `content`/`database` или
внести в план с отдельной зоной ответственности. Пока модуль остаётся вне плана,
он нарушает принцип «One Source of Truth».

## 11.3 Требует переработки

**Дублирование каркаса.** Шаблон из восьми файлов
(`dispatcher`, `resolver`, `handler`, `context`, `result`, `constants`, `utils`, `errors`)
повторён почти в каждом модуле: 99 файлов из 154 — это один и тот же абстрактный
паттерн без поведения. Он не описан ни в одной спецификации и противоречит принципам
«Small Components» и «Explicit over Implicit»: слои существуют не потому, что решают
задачу, а потому, что скопированы. При появлении `runtime/` большая их часть станет
мёртвым кодом, поэтому переработка `effects/` и `cards/` под Runtime должна начинаться
со снятия этого слоя, а не с надстройки над ним.

**Стек внутри состояния.** `GameState` содержит поле `stack: list[object]` и методы
`push` / `pop` / `reset_stack`, дублирующие `stack.Stack`. Это нарушает сразу два
правила: «State ничего не исполняет» и «One Source of Truth». Стек должен
существовать в одном месте — в `stack/`, а `GameState` должен ссылаться на него,
а не переопределять.

# 12. Ближайшие шаги

1. Создать `src/fsme/runtime/` по составу из раздела 6.1 и завести `tests/`.
2. Перевести `GameState` на единственный стек из `stack/`.
3. Переработать `effects/` под Runtime: `registry` + `executor` вместо
   `dispatcher`/`resolver`/`handler`.
4. Переработать `cards/`: `definition`, `registry`, `loader`, `validator` по
   `CARD_SCHEMA.md`.
5. Снять неиспользуемый каркас в модулях, не участвующих в этапах 1–2.
6. Принять решение по `resources/` (раздел 11.2).

Шаги 1–4 закрывают этап 1 и открывают этап 2.
