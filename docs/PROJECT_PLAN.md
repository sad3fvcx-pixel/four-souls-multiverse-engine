# 2. Продуктовая идея

> FSME — это не движок конкретного дополнения, а универсальный симулятор правил
> The Binding of Isaac: Four Souls, способный работать с оригинальными картами
> и пользовательским контентом через систему данных и DSL.

Из этого следуют четыре продуктовых требования:

| Требование | Что означает практически |
|---|---|
| Универсальность | Движок не знает ни одной конкретной карты по имени |
| Расширяемость | Новая карта = новый файл данных, а не новый код |
| Детерминизм | Один и тот же seed + один и тот же ввод = одна и та же партия |
| Проверяемость | Любая партия воспроизводима и покрывается автотестом |

`Syndrome of the Multiverse` — первый потребитель этих возможностей, но не
привилегированный: оригинальный набор и кастомные наборы проходят через один
и тот же content pipeline.

# 5. Слои и направление зависимостей

Список модулей не задаёт порядок сборки — его задают зависимости.
Зависимости разрешены **только сверху вниз**.

```
Слой 4   game                        управление партией
              ↓
Слой 3   runtime, rules              исполнение правил
              ↓
Слой 2   commands, effects, cards    доменные определения
              ↓
Слой 1   state, events, stack        данные и транспорт
              ↓
Слой 0   util, rng, config,          инфраструктура
         logging
```

Сквозные модули (`validation`, `serialization`, `replay`, `content`,
`database`, `plugins`) зависят от нижних слоёв и не зависят друг от друга.

Жёсткие правила:

1. `state` импортирует только `util` и контейнеры данных нижних слоёв
   (`stack.Stack`, `events.EventQueue`). Исполнителей, резолверов и `runtime`
   он не импортирует никогда.
2. `state` ничего не исполняет — он только хранит данные.
3. Мутировать `GameState` имеет право **только** `runtime`.
4. `cards` — данные; логика карт не живёт в `cards`.
5. Обратные импорты (снизу вверх) запрещены; при необходимости используется событие.

Правило 1 уточнено по итогам этапа 1: `GAME_STATE.md` §9-§10 и `STACK.md` §17
требуют, чтобы стек и очередь событий лежали внутри `GameState` — иначе
сохранение и replay не восстановят незавершённое разрешение. Спецификация
старше плана, поэтому `state` держит эти объекты, а запрет касается только
исполняющего кода.

Правило 3 — центральное. Оно превращает «Event Driven» и «Deterministic» из
намерения в проверяемое свойство: точка мутации одна, значит и точка записи
в replay-лог одна.

# 6. Ядро движка

## 6.1 `runtime/` — главный исполнитель

Отвечает за:

- запуск игры;
- выполнение команд;
- обработку событий;
- разрешение способностей;
- выполнение эффектов;
- контроль порядка действий.

```
runtime/
├── runtime.py
├── execution_context.py
├── ability_context.py
├── interpreter.py
├── effect_executor.py
├── condition_evaluator.py
├── target_resolver.py
└── errors.py
```

## 6.2 `state/` — игровое состояние

```
state/
├── game_state.py
├── player_state.py
├── turn_state.py
├── zones.py
├── card_state.py
└── combat_state.py
```

Принцип: State ничего не исполняет, он только хранит данные.

## 6.3 `game/` — фасад партии

```
game/
├── game.py
└── errors.py
```

Изначально планировались `turn_manager`, `phase_manager`, `victory` и
`rules_engine`. Все четыре — правила, и они живут в `rules/`: ход и фазы в
`rules/turn.py`, победа в State-Based Actions Runtime. В `game/` осталось то,
для чего он нужен снаружи — единая точка входа для UI, ИИ и сети.

## 6.4 `events/` — система событий

Основа реактивной архитектуры:

```
AttackCommand
     ↓
AttackEvent
     ↓
Trigger: "when_attack"
     ↓
Ability
     ↓
Effect
```

```
events/
├── event.py
├── bus.py
├── queue.py
├── dispatcher.py
├── listener.py
├── subscription.py
└── types.py
```

## 6.5 `stack/` — порядок выполнения

```
Effect A
Effect B
Reaction C
     ↓
Stack:
     C
     B
     A
```

```
stack/
├── stack.py
├── item.py
└── errors.py
```

Резолвера в `stack/` нет: разрешение требует эффектов, целей и событий, которые
лежат выше стека по зависимостям. Стек хранит порядок, разрешает — Runtime.

## 6.6 `rules/` — правила Four Souls

Обработчик команды отвечает на два вопроса: законно ли действие и что
происходит, когда его совершают. Валидация только читает состояние, поэтому
отклонённая команда не может оставить партию в половинчатом виде.

```
rules/
├── turn.py           # начало партии, фазы, конец хода
├── combat.py         # атака как последовательность раундов
├── loot.py           # розыгрыш добычи
├── activation.py     # активация предметов
├── shop.py           # покупка
├── priority.py       # передача приоритета
├── procedures.py     # процедуры, разрешаемые стеком
├── constants.py      # официальные числа
└── errors.py
```

Раунд боя кладётся в стек отдельным объектом. Поэтому между бросками успевают
разрешиться способности — ровно как требуют официальные правила, — и никакой
цикл внутри боя для этого не нужен: его двигает Runtime, разрешая стек.

## 7.2 `effects/` — библиотека действий

`gain_coins`, `deal_damage`, `draw_card`, `heal`, `add_bonus`, ...

```
effects/
├── effect.py
├── registry.py
├── context.py
└── builtin/
    ├── coins.py
    ├── damage.py
    ├── dice.py
    ├── loot.py
    └── modifiers.py
```

Исполнитель живёт в `runtime/effect_executor.py`, а не здесь: эффект описывает
операцию, Runtime её выполняет. `context.py` задаёт протокол — ровно тот набор
прав, который эффект получает от Runtime.

## 7.3 `abilities/` — Ability DSL

```yaml
trigger:
  type: activate

conditions:
  - has_charge

effects:
  - gain_loot: 1
```

Отдельного пакета `abilities/` по итогам этапа 1 не будет. Его четыре части
разошлись по местам, где у них уже есть владелец:

| `parser.py` | `runtime/interpreter.py` |
| `resolver.py` | `runtime/condition_evaluator.py`, `runtime/target_resolver.py` |

Пятый пакет между ними добавлял бы слой пересылки, а не решал задачу.

# 8. Card Maker

Отдельный инструмент, не часть движка:

```
tools/
└── card_editor/
```

Сценарий использования:

1. пользователь выбирает тип карты;
2. выбирает триггер;
3. добавляет эффекты;
4. сохраняет JSON;
5. движок автоматически проверяет карту.

Card Maker обязан использовать тот же `validation/`, что и движок —
второй реализации проверки быть не должно.

# 9. Этапы разработки

Каждый этап считается завершённым только по критерию выхода.
Общий Definition of Done из `DEVELOPMENT_GUIDELINES.md` применяется к каждому.

## Этап 1 — Фундамент

Состав: структура проекта, Runtime, State, Events, Stack.

Критерий выхода:
- `runtime/` существует и владеет единственной точкой мутации `GameState`;
- событие проходит путь `emit → listener → stack → resolve` в тесте;
- `tests/` запускается и зелёный.

## Этап 2 — Выполнение правил

Состав: Commands, Effects, Ability Resolver, DSL.

Критерий выхода:
- команда валидируется, исполняется и порождает события;
- способность, описанная в DSL, разрешается без кода под конкретную карту;
- реестры эффектов/триггеров/условий подключены к Runtime.

## Этап 3 — Первая рабочая партия

Цель — запустить сквозной сценарий:

```
Start Game
     ↓
Player Turn
     ↓
Attack
     ↓
Resolve Effect
     ↓
End Turn
```

Критерий выхода:
- партия из нескольких ходов доходит до конца без ручного вмешательства;
- один и тот же seed даёт побайтово одинаковый лог партии.

## Этап 4 — Официальный контент

Состав: оригинальные карты, монстры, предметы, персонажи.

Критерий выхода:
- `OFFICIAL_CARD_COVERAGE.md` отражает фактическое покрытие;
- каждая нереализованная карта имеет причину: отсутствующая механика, а не «нет кода».

## Этап 5 — Редактор карт

Состав: Card Maker, проверка карт, экспорт, импорт.

Критерий выхода:
- карта, созданная в редакторе, загружается движком без правок вручную.

## Этап 6 — Расширения

Состав: моды, пользовательские наборы, онлайн, ИИ-игроки, симуляции баланса.

Критерий выхода определяется отдельно при входе в этап.

## 11.4 Расхождения со спецификациями, найденные при реализации

| Где | Расхождение | Решение |
|---|---|---|
| `EVENT_SYSTEM.md` §4 | Событие содержит `timestamp` | Заменено на монотонный `sequence`: время сделало бы два прогона одного seed различными |
| Вся кодовая база | Идентификаторы через `uuid4()` | Заменены на счётчик внутри `GameState`: `uuid4` берёт случайность у ОС, что запрещено `RNG.md` §12 |
| `CONDITION_REGISTRY.md` | Условие `chance` | Не реализовано: бросок изменил бы состояние RNG, а условия обязаны быть чистыми. Вероятность — эффект, не условие |
| `TARGET_REGISTRY.md` | «Target никогда не изменяет состояние» + цели `random_*` | Случайные цели расходуют RNG по необходимости; исключение задокументировано в коде |
| `TRIGGER_REGISTRY.md` | Нет триггеров экономики, здоровья, фаз и розыгрыша | Добавлены `on_play`, `coins_gained`, `coins_lost`, `damage_dealt`, `healed`, `player_revived`, `phase_changed`; реестр дополнен на этапе 2 |
| `EFFECT_DSL_SPEC.md` | Сокращённая запись `{"gain_loot": 1}` | Параметр объявляет сам эффект (`primary`), иначе движку пришлось бы угадывать между `amount` и `count` |
| `COMMAND_SYSTEM.md` §7 | Нет команды смены фазы | Добавлена `end_phase`: игрок, не разыгравший добычу, иначе не может попасть в фазу действия |

## 11.5 Отклонения от официальных правил

`RULES_SPEC.md` §14 требует, чтобы каждое отклонение было задокументировано,
версионировано и по возможности отключаемо. Текущий список:

| Отклонение | Причина | Когда снимается |
|---|---|---|
| Приоритет по умолчанию выключен: все считаются спасовавшими немедленно | Без источника ввода партия зависла бы; нужно тестам, ИИ и симуляциям баланса | Отключаемо уже сейчас: `Runtime(interactive_priority=True)` |
| Монстр без напечатанных значений считается как «бросок 4, атака 1» | Значения по умолчанию для тестового контента | Вместе с официальным набором |
| В комнату нельзя войти командой | Движок открывает и закрывает комнату; когда и за какую цену — правило, которое придёт с картами | Вместе с официальным набором |
| Бросок открыт для ответа только при включённом приоритете | С `interactive_priority=False` отвечать некому, и окно только добавляло бы шаг; бросок разрешается на месте, как раньше | Отключаемо уже сейчас: `Runtime(interactive_priority=True)` |
| «Загадайте число до броска» не выражается | Нужно хранить предсказание игрока между двумя бросками | Блокирует Crystal Ball |
| Замещающая способность не может ничего спросить | Замещения выполняются внутри обработки события, а не на стеке, — приостановить их так же, как способность, сейчас нельзя | Вместе с приостановкой обработки события |
| Смерть нельзя предотвратить | Движок убивает через SBA непрерывно, а «prevent death» требует знать, в каком состоянии остаётся выживший. Формулировки в имеющихся спецификациях нет | Блокирует Broken Ankh, Guppy's Collar |
| Штрафов за смерть нет | «Before/after paying penalties» не к чему привязать; какие именно штрафы — в спецификациях не выписано | Блокирует Shadow, Baby Haunt, Daddy Haunt; у Bloody Penny, Greed's Gullet, Suicide King и Lazarus' Rags не соблюдается порядок |
| Игрока нельзя ни к чему принудить | Движок умеет разрешать и запрещать, но не обязывать | Блокирует Ambush!, Monster Manual |
| Голосование не выражается | Решение можно адресовать одному игроку (`chooser`), но не собрать ответы всего стола и не сравнить их | Блокирует Remote Detonator; у Judgement, Wizoob и Dank Globin выбор делает контроллер |
| Предмет нельзя скопировать | Копирование карты — отдельная механика: копия должна получить способности оригинала на срок | Блокирует Diplopia, Modeling Clay, Placebo, Blank Card |
| Отложенное замещение не выражается | «Следующий раз, когда…» без готового щита: урон уменьшается до 1, лут берётся из сброса, лут удваивается | Блокирует Mom's Bra, Compost, Two of Clubs, Host Hat |
| Стоимость способности не может требовать выбора | Оплата идёт без вопросов игроку, а «уничтожьте 2 предмета» — выбор | Блокирует Contract from Below |
| «Первый/каждый второй раз за ход» не считается | Нужен счётчик событий на карте, обнуляемый ходом | Блокирует The Habit, The Haunt |
| В колоде нельзя искать карту по имени | Поиск умеет тип и семейство, но не имя | Блокирует Peep |
| Урон нельзя разделить между целями | «2 damage divided as they choose» — одно решение о нескольких числах | Блокирует Pestilence |
| Монстра нельзя сделать неатакуемым, а награды — удвоить | Ограничения атаки и изменение выплаты наград движок не выражает | Блокирует Stoney, Dinga |
| Розыгрыш и активацию нельзя запретить другим | Ограничение на действия других игроков | Блокирует Trinity Shield |
| Розыгрыш «любого числа карт» не выражается | Неограниченная норма — не число | Блокирует Box! |
| Добор в фазу добычи не реализован | Правило «в начале хода возьмите 1 карту добычи» в имеющихся спецификациях не выписано, а придумывать его нельзя | Блокирует Mom's Purse, Mom's Coin Purse; частично There's Options, The D10, Cheese Grater |
| Cain и Eden не реализованы | «Ходишь первым» и «выбери стартовый предмет из трёх» — правила раскладки, а не способности карты | Вместе с настраиваемой раскладкой |
| Приоритет по умолчанию выключен: все считаются спасовавшими немедленно | Без источника ввода партия зависла бы; нужно тестам, ИИ и симуляциям баланса | Отключаемо уже сейчас: `Runtime(interactive_priority=True)` |
| Монстр без напечатанных значений считается как «бросок 4, атака 1» | Значения по умолчанию для тестового контента | Вместе с официальным набором |
| В комнату нельзя войти командой | Движок открывает и закрывает комнату; когда и за какую цену — правило, которое придёт с картами | Вместе с официальным набором |
| Украденный из магазина предмет не восполняется сразу | Магазин пополняется правилом покупки; кража идёт мимо него | Вместе с общим пополнением магазина |
| Добычу можно разыграть в ответ, по одной карте на игрока за ход | `STACK.md` §9 прямо разрешает разыгрывать добычу в окне приоритета, но норму розыгрышей вне своего хода спецификации не задают | Когда правило будет выписано |
| «Обязан атаковать ещё раз» реализовано как «может» | Движок не умеет обязывать; лишняя атака выдаётся, принуждения нет | Блокирует точность Conquest, Envy, Portal |

# 12. Ближайшие шаги

Этапы 1-3 закрыты: Runtime владеет единственной точкой мутации, партия целиком
идёт через команды, запись партии воспроизводится побайтово.

Этап 4 закрыт по инженерной части. Конвейер контента реализован полностью,
каталог `content/` создан, раскладка партии из библиотеки работает.

Недостающие механики добраны отдельным заходом: комнаты, проклятия, вечные
предметы, кража и уничтожение предметов, копирование, поиск в колоде,
бонусные души, условные статики и модификация броска. Список «не
поддерживается» в `OFFICIAL_CARD_COVERAGE.md` сократился с девяти пунктов до
четырёх, и каждый из четырёх ждёт либо официальных формулировок правил, либо
расширения приоритета.

Официальный набор внесён: 1014 карт из выверенной базы, 21 набор,
`tools/import_cards.py` конвертирует базу в контент и не додумывает то, чего в
ней нет. Напечатанные числа, тексты и связи персонаж → стартовый предмет
проверяются тестами.

Импортировать карту и реализовать её — разные работы. Импорт даёт имя, тип и
напечатанные числа; поведение пишется руками по английскому тексту карты и
живёт в `content/<набор>/_abilities.json` — накладке, которую импорт
подмешивает к сгенерированным файлам и не затирает при повторном запуске.
Поэтому пересборка базы никогда не теряет написанное поведение, а
`OFFICIAL_CARD_COVERAGE.md` генерируется из контента и не может разойтись с
ним.

Базовая игра: **234 карты реализовано, 17 без правил, 36 осталось**. Ни одна из
оставшихся не ждёт кода — каждая ждёт механики или формулировки правил, и все
они выписаны в §11.5 с указанием, что именно блокирует. Окно приоритета внутри броска — самое крупное, что мешало, — сделано:
бросок останавливается, стол отвечает, и только потом результат считается.

Механики, добранные по ходу — каждая написана для карты, но ни одна не
привязана к ней: временные модификаторы и щиты урона; тринкеты, лишний ход,
пропуск хода, отмена стека и завершение хода эффектом; порядок колоды и
раскладка «положите обратно в любом порядке»; `may` и `choose` в языке карт;
значения, которые способность узнаёт на ходу (`from`, `from_event`,
`last_result`, `count`); платные способности с ценой в монетах, картах,
счётчиках и хитах; область `controller`; собственные числа монстров; слоты
монстров и магазина как состояние; цена магазина как характеристика; бонусные
души на столе; атрибуция боевого урона; вопрос, адресованный не контроллеру
способности (`chooser`), и передача карт из рук в руки — дарением и обменом.
