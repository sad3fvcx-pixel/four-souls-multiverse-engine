Этот документ фиксирует общий план разработки FSME как отдельного технического проекта.

# 2. Продуктовая идея

> FSME — это не движок конкретного дополнения, а универсальный симулятор правил
> The Binding of Isaac: Four Souls, способный работать с оригинальными картами
> и пользовательским контентом через систему данных и DSL.

Из этого следуют четыре продуктовых требования:

| Требование | Что означает практически |
|---|---|
| Универсальность | Движок не знает ни одной конкретной карты по имени |
| Расширяемость | Новая карта = новый файл данных, а не новый код |
| Детерминизм | Один и тот же seed + один и тот же ввод = одна и та же партия |
| Проверяемость | Любая партия воспроизводима и покрывается автотестом |

`Syndrome of the Multiverse` — первый потребитель этих возможностей, но не
привилегированный: оригинальный набор и кастомные наборы проходят через один
и тот же content pipeline.

# 5. Слои и направление зависимостей

Список модулей не задаёт порядок сборки — его задают зависимости.
Зависимости разрешены **только сверху вниз**.

```
Слой 4   game                        управление партией
              ↓
Слой 3   runtime, rules              исполнение правил
              ↓
Слой 2   commands, effects, cards    доменные определения
              ↓
Слой 1   state, events, stack        данные и транспорт
              ↓
Слой 0   util, rng, config,          инфраструктура
         logging
```

Сквозные модули (`validation`, `serialization`, `replay`, `content`,
`database`, `plugins`) зависят от нижних слоёв и не зависят друг от друга.

Жёсткие правила:

1. `state` импортирует только `util` и контейнеры данных нижних слоёв
   (`stack.Stack`, `events.EventQueue`). Исполнителей, резолверов и `runtime`
   он не импортирует никогда.
2. `state` ничего не исполняет — он только хранит данные.
3. Мутировать `GameState` имеет право **только** `runtime`.
4. `cards` — данные; логика карт не живёт в `cards`.
5. Обратные импорты (снизу вверх) запрещены; при необходимости используется событие.

Правило 1 уточнено по итогам этапа 1: `GAME_STATE.md` §9-§10 и `STACK.md` §17
требуют, чтобы стек и очередь событий лежали внутри `GameState` — иначе
сохранение и replay не восстановят незавершённое разрешение. Спецификация
старше плана, поэтому `state` держит эти объекты, а запрет касается только
исполняющего кода.

Правило 3 — центральное. Оно превращает «Event Driven» и «Deterministic» из
намерения в проверяемое свойство: точка мутации одна, значит и точка записи
в replay-лог одна.

# 6. Ядро движка

## 6.1 `runtime/` — главный исполнитель

Отвечает за:

- запуск игры;
- выполнение команд;
- обработку событий;
- разрешение способностей;
- выполнение эффектов;
- контроль порядка действий.

```
runtime/
├── runtime.py
├── execution_context.py
├── ability_context.py
├── interpreter.py
├── effect_executor.py
├── condition_evaluator.py
├── target_resolver.py
└── errors.py
```

## 6.2 `state/` — игровое состояние

```
state/
├── game_state.py
├── player_state.py
├── turn_state.py
├── zones.py
├── card_state.py
└── combat_state.py
```

Принцип: State ничего не исполняет, он только хранит данные.

## 6.3 `game/` — фасад партии

```
game/
├── game.py
└── errors.py
```

Изначально планировались `turn_manager`, `phase_manager`, `victory` и
`rules_engine`. Все четыре — правила, и они живут в `rules/`: ход и фазы в
`rules/turn.py`, победа в State-Based Actions Runtime. В `game/` осталось то,
для чего он нужен снаружи — единая точка входа для UI, ИИ и сети.

## 6.4 `events/` — система событий

Основа реактивной архитектуры:

```
AttackCommand
     ↓
AttackEvent
     ↓
Trigger: "when_attack"
     ↓
Ability
     ↓
Effect
```

```
events/
├── event.py
├── bus.py
├── queue.py
├── dispatcher.py
├── listener.py
├── subscription.py
└── types.py
```

## 6.5 `stack/` — порядок выполнения

```
Effect A
Effect B
Reaction C
     ↓
Stack:
     C
     B
     A
```

```
stack/
├── stack.py
├── item.py
└── errors.py
```

Резолвера в `stack/` нет: разрешение требует эффектов, целей и событий, которые
лежат выше стека по зависимостям. Стек хранит порядок, разрешает — Runtime.

## 6.6 `rules/` — правила Four Souls

Обработчик команды отвечает на два вопроса: законно ли действие и что
происходит, когда его совершают. Валидация только читает состояние, поэтому
отклонённая команда не может оставить партию в половинчатом виде.

```
rules/
├── turn.py           # начало партии, фазы, конец хода
├── combat.py         # атака как последовательность раундов
├── loot.py           # розыгрыш добычи
├── activation.py     # активация предметов
├── shop.py           # покупка
├── priority.py       # передача приоритета
├── procedures.py     # процедуры, разрешаемые стеком
├── constants.py      # официальные числа
└── errors.py
```

Раунд боя кладётся в стек отдельным объектом. Поэтому между бросками успевают
разрешиться способности — ровно как требуют официальные правила, — и никакой
цикл внутри боя для этого не нужен: его двигает Runtime, разрешая стек.

## 7.2 `effects/` — библиотека действий

`gain_coins`, `deal_damage`, `draw_card`, `heal`, `add_bonus`, ...

```
effects/
├── effect.py
├── registry.py
├── context.py
└── builtin/
    ├── coins.py
    ├── damage.py
    ├── dice.py
    ├── loot.py
```

Исполнитель живёт в `runtime/effect_executor.py`, а не здесь: эффект описывает
операцию, Runtime её выполняет. `context.py` задаёт протокол — ровно тот набор
прав, который эффект получает от Runtime.

## 7.3 `abilities/` — Ability DSL

```yaml

  type: activate

conditions:
  - has_charge
```

Отдельного пакета `abilities/` по итогам этапа 1 не будет. Его четыре части
разошлись по местам, где у них уже есть владелец:

| `parser.py` | `runtime/interpreter.py` |
| `resolver.py` | `runtime/condition_evaluator.py`, `runtime/target_resolver.py` |

Пятый пакет между ними добавлял бы слой пересылки, а не решал задачу.

# 8. Card Maker

Отдельный инструмент, не часть движка:

```
tools/
└── card_editor/
```

Сценарий использования:

1. пользователь выбирает тип карты;
2. выбирает триггер;
3. добавляет эффекты;
4. сохраняет JSON;
5. движок автоматически проверяет карту.

Card Maker обязан использовать тот же `validation/`, что и движок —
второй реализации проверки быть не должно.

# 9. Этапы разработки

Каждый этап считается завершённым только по критерию выхода.
Общий Definition of Done из `DEVELOPMENT_GUIDELINES.md` применяется к каждому.

## Этап 1 — Фундамент

Состав: структура проекта, Runtime, State, Events, Stack.

Критерий выхода:
- `runtime/` существует и владеет единственной точкой мутации `GameState`;
- событие проходит путь `emit → listener → stack → resolve` в тесте;
- `tests/` запускается и зелёный.

## Этап 2 — Выполнение правил

Состав: Commands, Effects, Ability Resolver, DSL.

Критерий выхода:
- команда валидируется, исполняется и порождает события;
- способность, описанная в DSL, разрешается без кода под конкретную карту;
- реестры эффектов/триггеров/условий подключены к Runtime.

## Этап 3 — Первая рабочая партия

Цель — запустить сквозной сценарий:

```
Start Game
     ↓
Player Turn
     ↓
Attack
     ↓
Resolve Effect
     ↓
End Turn
```

Критерий выхода:
- партия из нескольких ходов доходит до конца без ручного вмешательства;
- один и тот же seed даёт побайтово одинаковый лог партии.

## Этап 4 — Официальный контент

Состав: оригинальные карты, монстры, предметы, персонажи.

Критерий выхода:
- `OFFICIAL_CARD_COVERAGE.md` отражает фактическое покрытие;
- каждая нереализованная карта имеет причину: отсутствующая механика, а не «нет кода».

## Этап 5 — Редактор карт

Состав: Card Maker, проверка карт, экспорт, импорт.

Критерий выхода:
- карта, созданная в редакторе, загружается движком без правок вручную.

## Этап 6 — Расширения

Состав: моды, пользовательские наборы, онлайн, ИИ-игроки, симуляции баланса.

Критерий выхода определяется отдельно при входе в этап.

## 11.4 Расхождения со спецификациями, найденные при реализации

| Где | Расхождение | Решение |
|---|---|---|
| `EVENT_SYSTEM.md` §4 | Событие содержит `timestamp` | Заменено на монотонный `sequence`: время сделало бы два прогона одного seed различными |
| Вся кодовая база | Идентификаторы через `uuid4()` | Заменены на счётчик внутри `GameState`: `uuid4` берёт случайность у ОС, что запрещено `RNG.md` §12 |
| `CONDITION_REGISTRY.md` | Условие `chance` | Не реализовано: бросок изменил бы состояние RNG, а условия обязаны быть чистыми. Вероятность — эффект, не условие |
| `TARGET_REGISTRY.md` | «Target никогда не изменяет состояние» + цели `random_*` | Случайные цели расходуют RNG по необходимости; исключение задокументировано в коде |
| `TRIGGER_REGISTRY.md` | Нет триггеров экономики, здоровья, фаз и розыгрыша | Добавлены `on_play`, `coins_gained`, `coins_lost`, `damage_dealt`, `healed`, `player_revived`, `phase_changed`; реестр дополнен на этапе 2 |
| `EFFECT_DSL_SPEC.md` | Сокращённая запись `{"gain_loot": 1}` | Параметр объявляет сам эффект (`primary`), иначе движку пришлось бы угадывать между `amount` и `count` |
| `COMMAND_SYSTEM.md` §7 | Нет команды смены фазы | Добавлена `end_phase`: игрок, не разыгравший добычу, иначе не может попасть в фазу действия |

## 11.5 Отклонения от официальных правил

`RULES_SPEC.md` §14 требует, чтобы каждое отклонение было задокументировано,
версионировано и по возможности отключаемо. Текущий список:

| Отклонение | Причина | Когда снимается |
|---|---|---|
| Приоритет по умолчанию выключен: все считаются спасовавшими немедленно | Без источника ввода партия зависла бы; нужно тестам, ИИ и симуляциям баланса | Отключаемо уже сейчас: `Runtime(interactive_priority=True)` |
| Монстр без напечатанных значений считается как «бросок 4, атака 1» | Значения по умолчанию для тестового контента | Вместе с официальным набором |
| Бросок открыт для ответа только при включённом приоритете | С `interactive_priority=False` отвечать некому, и окно только добавляло бы шаг; бросок разрешается на месте, как раньше | Отключаемо уже сейчас: `Runtime(interactive_priority=True)` |
| Замещающая способность не может ничего спросить | Замещения выполняются внутри обработки события, а не на стеке, — приостановить их так же, как способность, сейчас нельзя | Блокирует Sacred Heart; вместе с приостановкой обработки события |
| Смерть применяется, когда движок останавливается, а не посреди вопроса | Смерть — SBA, а SBA берутся, когда очередь пуста; пока способность стоит на вопросе, игрок на 0 HP ещё жив. `COMPREHENSIVE_RULES.md` §10 говорит то же: смерть встаёт в очередь и ждёт своего места | Никогда: это и есть правило |
| Бесконечный цикл между картами останавливает партию ошибкой | Правила о циклах в спецификациях нет. Placebo копирует способность предмета, Rainbow Tapeworm становится копией предмета — вместе они копируют друг друга без конца (сиды 8 и 58 на двоих). Движок называет, что зациклилось, и останавливается; выдумывать правило вместо этого нельзя | Когда в спецификации появится правило о циклах |
| Слот комнаты один, и расширить его нельзя | `COMPREHENSIVE_RULES.md` §12 говорит о «слоте комнаты» в единственном числе; сколько комнат может лежать сразу и что делает лишний слот, не выписано | У Mulligan (alt) выбор из двух областей вместо трёх |
| Ни одна из 68 карт комнат не написана | Механика комнат есть; поведение конкретных карт пишется руками по их тексту, как у любого набора | Вместе с наборами Requiem, Warp Zone и остальными |
| Штраф за смерть платит сам умерший | Что именно теряется, выбирает тот, кто умер, и потерянное уходит в сброс; передать выбор и потерянное другому игроку нельзя | Блокирует Shadow |
| Смотреть верхнюю карту колоды нельзя «в любой момент» | Просмотр — это информация, а не изменение партии: у движка нет закрытой информации, которую можно было бы открыть одному игроку. Разрешения без последствий для состояния нечего исполнять | У There's Options реализована только вторая половина — дополнительная покупка |
| У Judgement, Wizoob и Dank Globin выбор делает контроллер, а не тот, кого карта называет | Точность этих трёх карт, а не механика: голосование и `chooser` уже есть | Когда до них дойдут руки |
| Копию разыгрываемой карты нельзя сделать | `watch_for` дожидается события, но скопировать саму разыгранную карту — отдельная механика | Блокирует Blank Card |
| Стоимость способности не может требовать выбора | Оплата идёт без вопросов игроку, а «уничтожьте 2 предмета» — выбор | Блокирует Contract from Below |
| Ключевое слово Indomitable не реализовано | Что именно оно запрещает, в имеющихся спецификациях не выписано | Блокирует Delirium (alt), Mega Satan! (alt), The Beast (alt) |
| Бой, в котором три раунда подряд ничьи хиты не менялись, прекращается | Атака заканчивается чьей-то смертью; если ни одна сторона не может нанести урон, раунды шли бы вечно. Это предохранитель движка, а не правило: на картах его нет, и любая атака, где урон проходит, счётчик обнуляет | Никогда: команда обязана завершаться |
| Партию нельзя сохранить, пока способность не дорешена | Очередь операций и место в ней — рабочая память интерпретатора, она нигде не записана и восстанавливается из карты заново | Вместе с записью состояния интерпретатора |
| Объявление покупки и атаки тратит ход сразу, а «фи-зл» его возвращает | `COMPREHENSIVE_RULES.md` §12 говорит только, что несостоявшаяся покупка или атака «не потрачена»; в каком порядке это считается, не выписано. Движок тратит при объявлении, чтобы нельзя было поставить в очередь два объявления и выбрать выжившее, и возвращает при фи-зле | Никогда: наблюдаемый результат совпадает с правилом |
| Украденный из магазина предмет не восполняется сразу | Магазин пополняется правилом покупки; кража идёт мимо него | Вместе с общим пополнением магазина |
| Добычу можно разыграть в ответ, по одной карте на игрока за ход | `STACK.md` §9 прямо разрешает разыгрывать добычу в окне приоритета, но норму розыгрышей вне своего хода спецификации не задают | Когда правило будет выписано |

# 12. Ближайшие шаги

Этапы 1-3 закрыты: Runtime владеет единственной точкой мутации, партия целиком
идёт через команды, запись партии воспроизводится побайтово.

Этап 4 закрыт по инженерной части. Конвейер контента реализован полностью,
каталог `content/` создан, раскладка партии из библиотеки работает.

Недостающие механики добраны отдельным заходом: комнаты, проклятия, вечные
предметы, кража и уничтожение предметов, копирование, поиск в колоде,
бонусные души, условные статики и модификация броска. Список «не
поддерживается» в `OFFICIAL_CARD_COVERAGE.md` сократился с девяти пунктов до
четырёх, и каждый из четырёх ждёт либо официальных формулировок правил, либо
расширения приоритета.

Официальный набор внесён: 1014 карт из выверенной базы, 21 набор,
`tools/import_cards.py` конвертирует базу в контент и не додумывает то, чего в
ней нет. Напечатанные числа, тексты и связи персонаж → стартовый предмет
проверяются тестами.

Импортировать карту и реализовать её — разные работы. Импорт даёт имя, тип и
напечатанные числа; поведение пишется руками по английскому тексту карты и
живёт в `content/<набор>/_abilities.json` — накладке, которую импорт
подмешивает к сгенерированным файлам и не затирает при повторном запуске.
Поэтому пересборка базы никогда не теряет написанное поведение, а
`OFFICIAL_CARD_COVERAGE.md` генерируется из контента и не может разойтись с
ним.

Базовая игра: **265 карт реализовано, 17 без правил, 5 осталось**.

Начат набор `alt_art`: **41 карта реализована, 1 без правил, 20 осталось**.

Малые наборы: `g_fuel`, `gish`, `nendoroid`, `retro`, `youtooz`,
`the_legend_of_bum_bo` и `dick_knots` закрыты целиком; в `target`,
`mewgenics`, `tapeworm`, `star` и `challenges` осталось по одной-пяти карт,
и каждая — из-за механики, а не из-за кода. Тесты — `tests/test_promo_cards.py`.
Это не перепечатка базовой игры — у карт с теми же именами другой текст:
альтернативный Larry Jr. получает +1 AT там, где напечатанный получает +1 DC.
Поэтому каждая карта читается заново и проверяется своим тестом
(`tests/test_alt_art_cards.py`).

Из оставшихся в базовой игре ни одна не ждёт кода — каждая ждёт механики или
формулировки правил, и все они выписаны в §11.5 с указанием, что именно
блокирует. В `alt_art` к тем же причинам добавились свои: у слотов монстров нет
личности («атакуйте монстра в одном из этих слотов»), статика не умеет расти от
счётчиков на карте, и ключевое слово «Indomitable» в спецификациях не выписано. Окно приоритета внутри броска — самое крупное, что мешало, — сделано:
бросок останавливается, стол отвечает, и только потом результат считается.

Механики, добранные по ходу — каждая написана для карты, но ни одна не
привязана к ней: временные модификаторы и щиты урона; тринкеты, лишний ход,
пропуск хода, отмена стека и завершение хода эффектом; порядок колоды и
раскладка «положите обратно в любом порядке»; `may` и `choose` в языке карт;
значения, которые способность узнаёт на ходу (`from`, `from_event`,
`last_result`, `count`); платные способности с ценой в монетах, картах,
счётчиках и хитах; область `controller`; собственные числа монстров; слоты
монстров и магазина как состояние; цена магазина как характеристика; бонусные
души на столе; атрибуция боевого урона; вопрос, адресованный не контроллеру
способности (`chooser`), и передача карт из рук в руки — дарением и обменом;
обещания (`promise`) — изменение события, которое ещё не произошло, когда
карты, обещавшей его, уже нет; счётчик срабатываний за ход — «первый раз
за ход» и «каждый второй раз за ход»; передача рук по кругу и уничтожение
предмета, предложенное к замещению; лицо карты — правила, по которым карта
сейчас играет, не теряя того, чем она напечатана; запреты — статика, которая
отвечает не числом, а «нельзя»; смерть, предложенная к замещению;
обязанности хода — то, что игрок должен сделать, «если может»; наблюдатели
(`watch_for`) — способность, ждущая события, когда карты уже нет;
голосование стола и подсчёт голосов; урон, разделённый между целями;
снятая норма — «сколько угодно» вместо числа; кто ходит первым — вопрос
раскладки к розданным персонажам; вечность, выданная одной карте в игре;
переворот броска, случайный предмет и выбор любого персонажа как цель;
счётчик срабатываний, считающий только то, что подходит карте; обещание,
выбирающее событие по тому, что оно несёт; предметы, отобранные по
счётчикам на них; статика, растущая от счётчиков на своей карте; счётчик,
отнимающий у карты её правила, пока лежит на ней; результат эффекта,
сохранённый под своим именем, и сравнение сохранённого; вид цели, который
несёт событие урона; лечение «до полного»; отмена своей атаки; предмет,
пропускающий одну перезарядку; цена в именованных счётчиках.

Сохранение и загрузка партии сделаны (`fsme.serialization.save_game` /
`load_game`, `Game.save()` / `Game.load()`): карта записывается один раз в той
зоне, где лежит, а всё, что на неё ссылается — стек, очередь событий, бой,
обещания — ссылается по идентификатору. Проверяется не файлом, а будущим:
сохранённая партия и та, из которой её сохранили, доигрываются рядом и должны
оставаться одной партией.

Партии целиком гоняются в `tests/test_soak.py`: стол из сценарных игроков
делает всё, что законно, на нескольких сидах и составах. Так нашлись три
ошибки, которых карточные тесты не видели: атака, пережившая свой ход; два
эффекта, падавших там, где должны молчать; и бой, в котором ни одна сторона не
может нанести урон.

Дальше:

1. Продолжать по наборам: сокровища и монстры базовой игры, затем
   расширения. Порядок работы тот же — читать текст, писать способность,
   писать тест, обновлять покрытие.
2. Этап 5 — редактор карт в `tools/card_editor/`, использующий тот же
   валидатор и тот же словарь движка, что и загрузчик.

# 13. Направление после ядра: аналитический движок

Ядро закрыто: партия эмулируется целиком. Дальнейшее развитие идёт не в сторону
ещё одного Tabletop Simulator, а в сторону инструмента, который **понимает,
записывает и анализирует** партии. Уникальность FSME не в том, что он играет, а
в том, что он способен провести тысячи партий и превратить игровой процесс в
данные.

```
FSME
├── Play          обычная партия              — есть
├── Journal       расширенный журнал партии   — есть
├── Replay        просмотр партий             — есть (воспроизведение из журнала)
├── Analytics     статистика                  — есть
├── Simulation    массовые прогоны            — есть
├── Card Testing  проверка контента           — есть
├── Bot           игрок, чьи рассуждения читаемы — есть
├── Study         объяснимые отчёты по прогону  — есть
├── Explain       разбор одной партии           — есть
├── Report        одна партия целиком           — есть (`fsme report`)
├── Desk          всё это на одной странице     — есть (`fsme desk`)
└── Content Tools пользовательские карты      — отдельная ветка
```

## 13.1 Журнал как основа

Выбран сознательно как первый шаг: из него естественно вырастают и replay, и
аналитика, и тестирование карт, потому что все трое читают одно и то же.

Одна запись на каждую принятую команду:

- где стояла партия (ход, фаза, кто чего ждёт, очередь, игроки);
- что движок принял бы вместо этого (`--offers`, по запросу);
- что было выбрано — командой и словами клиента;
- всё, что из этого вышло: каждое событие с его полезной нагрузкой;
- отпечаток позиции после команды.

Ничего из этого журнал не вычисляет: события — события движка, ходы — ответы
его же валидаторов. Он сохраняет то, что раньше выбрасывалось.

Из этого следуют два свойства, и оба — суть замысла. Журнал **воспроизводим**:
в нём лежат команды, и `fsme replay` прогоняет их через обычный движок, громко
расходясь на первой записи, чей отпечаток больше не сходится. И журнал —
**данные**: посчитать что-либо по десяти тысячам партий значит прочитать файлы,
а не дописать измерения в движок.

**Цена** (2 игрока, партия до победителя, замерено): 0.53 с без журнала, 0.67 с
с журналом, 0.71 с с журналом и альтернативами; 117 КБ на партию. Для 10 000
партий это ~1.2 ГБ — так что журналы имеет смысл писать по одному файлу на
партию и сжимать, когда до массовых прогонов дойдут руки.

## 13.2 Что вырастает дальше

| Направление | Состояние | Чего не хватает |
|---|---|---|
| Analytics | `fsme.analysis`: тэлли по персонажам, картам, монстрам и событиям | Ничего для базовых вопросов |
| Simulation | `fsme simulate --games N --jobs 4`: прогон, отчёт, журналы на диск | Ничего; 4 ядра дают ~6× |
| Card Testing | `fsme test-card <id>`: два прогона, разница с оценкой шума | Парность: изъятие карты перетасовывает всё |
| Decision logging | `fsme.bot`: эвристический бот, его арифметика ложится в журнал | Ничего для базового вопроса «почему бот так сходил» |
| Turning points | `fsme explain --moments N`: где партия решилась, по её же событиям | Контрфактов нет: другие линии игры не проигрываются |
| Decision analysis | `fsme explain --decisions N`: переигровка и взвешивание ходов ботом | Эталон слаб — бот на один ход вперёд |
| Замкнутый цикл | `study` → «worth testing next» → `test-card --from-study` → вердикт | Ничего для базового прохода |

## 13.3 Чего числа не говорят

Отчёт считает только то, что записано, и назван так, чтобы не обещать
большего. Колонка «won %» у карты — это доля партий, где выигравший держал
карту, а не вклад карты в победу: карту, которую чаще берёт уже выигрывающий,
такая таблица поднимет наверх безо всяких оснований. Разделить корреляцию и
эффект умеет только сравнение двух прогонов — с картой и без, — и это
следующий инструмент, а не другая колонка в этом.

Второе: играет стол, выбирающий случайно среди законных ходов. 41 смерть за
партию и 153 хода — это свойство случайной игры, а не игры. Числа сравнимы
между собой (одинаковый игрок), но не переносимы на живой стол.

## 13.4 Аналитический слой поверх журнала

Ядро не менялось: слой читает то, что движок уже записал. Ключевое
архитектурное решение — **сводка на партию** (`analysis/summary.py`): журнал в
117 КБ сводится к килобайту фактов по местам (души и откуда они, убийства,
смерти, монеты, покупки, использованные карты, ходы и сколько из них были
безальтернативными). Все отчёты читают сводки, поэтому прогон на десять тысяч
партий остаётся ровным по памяти, а любое число возвращается к своему сиду.

| Отчёт | Что отвечает |
|---|---|
| `fsme explain` | почему **эта** партия так закончилась: из чего сложились души победителя и что он делал иначе остальных |
| `fsme study` | что говорит **прогон**: откуда берутся души вообще, что идёт вместе с победой, какие карты ходят парами, что делает бот, какие партии стоит посмотреть руками |

**Три оговорки встроены в формулировки, а не оставлены читателю:**

1. Победители сравниваются с проигравшими — и всё, что их разделяет, столько же
   симптом, сколько причина: игрок, убивший четырёх монстров, выиграл отчасти
   поэтому и убил четвёртого отчасти потому, что уже выигрывал. Формулировка —
   «шло вместе с победой», никогда «привело к победе».
2. Пары карт: при сотнях карт пар десятки тысяч, поэтому верх любой такой
   таблицы поразителен по одной арифметике. Пара печатается только если
   встретилась не меньше пяти раз, рядом стоит lift и число партий, и написано
   прямо: строка отсюда — гипотеза для `fsme test-card`, а не синергия.
3. Аномалии — это правила, а не суждения: каждое названо и говорит, на что
   смотрело, поэтому читатель может отвергнуть одно, не переставая доверять
   остальным.

Единственное касание ядра: событие `soul_gained` теперь называет, чем душа
заработана. Это не механика — это полнота записи: без источника нельзя сказать,
выиграна ли партия на монстрах или на картах, а восстановить это потом
неоткуда.

## 13.5 Бот и логирование решений

Бот `heuristic-1` думает на один ход вперёд и знает четыре вещи: души
выигрывают, смерть дорога, у кубика шесть граней, предмет стоит 10¢. Он не
сильный и не пытается им быть — он **читаемый**: бот, чьи рассуждения можно
прочесть, это бот, чьи ошибки можно найти.

В журнал ложится **та самая арифметика, которой он считал**, а не пересказ:
выбранный ход с его слагаемыми и всё, что он перевесил. Если бы эти два могли
разойтись, журнал был бы бесполезен для единственной своей задачи.

Отдельно о названиях. Ничто здесь не зовётся «шансом на победу»: бот, думающий
на один ход, этого знать не может, а число с таким именем ему поверят. То, что
он знает точно — вероятность, что кубик даст достаточно; убьёт ли промах, —
названо тем, чем является; то, что он лишь предпочитает, названо
предпочтением, и вес рядом можно прочесть и оспорить.

**Измерено, а не предположено:** за столом из четверых, где место 0 играет бот,
а остальные случайно, бот выиграл **138 партий из 200 (69%)**. За полностью
случайным столом того же размера места делят победы 52 / 47 / 48 / 52, то есть
то же место даёт случайному игроку около 26%.

Первый замер был получен с изъяном, который нашёлся при разборе отчёта:
`legal_moves` перечисляет ходы **всех** игроков — включая карты, которыми
другие могут ответить, — и бот их брал. Стол, где каждый играет чужими картами,
не тот стол, на котором кого-то можно сравнивать. Теперь каждый играет только
свои ходы, и цифры выше — после исправления.

## 13.6 Пределы теста карты

Изъятие карты из колоды перетасовывает **каждую** партию, которую эта колода
раздаёт, — значит два прогона отличаются везде, а не только там, где карта.
Поэтому:

- если карта дошла до стола меньше чем в 10% партий, отчёт **не помечает**
  ни одной разницы и говорит, что видит колоду, а не карту;
- разница всегда печатается со своей неопределённостью, и «звёздочка» —
  это только «больше двух стандартных ошибок», а не «карта это сделала»;
- партии не парные: тот же сид без карты раздаёт другую партию. Сравниваются
  две совокупности, а не две версии одной партии.

Отдельный случай — стартовые предметы: без них персонаж, который на них
ссылается, не раскладывается, и прогон «без карты» получается короче. Отчёт
считает такие партии и говорит, что сравнение неравное.

## 13.7 Что симуляция уже нашла

Первый же прогон с новыми сидами уронил партию на сиде 100 и вывел на две
настоящие ошибки — ровно то, ради чего он и нужен:

- `owned_treasure` игнорировал `exclude_eternal`, хотя карта об этом просила:
  The D4 перебирал и вечный предмет тоже — уничтожить его не мог, а замену
  выдавал, так что игрок получал предметов больше, чем терял;
- The D20 и The D4 отдавали новый предмет цели по умолчанию — карте, а не
  игроку, и падали при активации;
- `give_treasure` падал, когда отдавать некому: в партии на двоих, где второй
  игрок мёртв, «отдайте предмет другому игроку» не называет никого. Остальные
  эффекты в такой ситуации молча пропускают инструкцию — теперь и этот.


## 13.8 Углубление аналитики: моменты, решения, замкнутый цикл

Три вопроса, на которые прошлый слой не отвечал: **где** партия решилась,
**какие решения** были рискованными и **что делать** с картой, которая
выглядит подозрительно. Ядро снова не менялось.

### Где партия решилась (`analysis/moments.py`)

Каждая запись журнала несёт события, которые она вызвала, а события прямым
текстом говорят, сколько душ получено, сколько монет перешло, сколько урона
прошло и кто умер. Вес хода — то, что **его собственные события** сделали с
отрывом будущего победителя от стола. Ничего не симулируется и не
экстраполируется.

Валюта табло названа и спорна: душа — 1.0 (партия это четыре штуки), цент —
0.01 (десять покупают предмет), хит-поинт — 0.02, смерть — −0.15 сверх
хит-поинтов. Читатель, не согласный с весами, может их игнорировать: каждый
момент печатается с душами, центами и хит-поинтами, которые он сдвинул, а это
уже счёт, а не мнение.

Две оговорки в коде, а не в голове читателя:

- **контрфактического утверждения нет.** «Партия пошла отсюда» — не «партия
  обязана была пойти отсюда»: ни одна другая линия игры не проигрывалась. Отчёт
  говорит это дословно;
- **момент бывает большим без чьего-либо решения.** Броски, случившиеся при
  разрешении хода, печатаются гранями, и момент помечается как решённый
  кубиком. Показывается шанс **первого** броска: перебросок — это второе
  решение, и приписывать атакующему знание о нём нельзя.

Из типичной партии на троих (433 хода) события двигают табло в 82 ходах, и три
самых крупных — это, как правило, три убитых монстра.

### Какие решения были рискованными (`analysis/risk.py`)

В журнале нет мнения о том, какой ход был лучше, потому что у движка мнения
нет. Поэтому мнение приносится: партия переигрывается обычным движком, и на
каждом ходу бота просят **взвесить всё, что было предложено**. Разрыв между
сыгранным и лучшим по мнению бота — и есть число.

Это **разногласие, а не ошибка**, и формулировки нигде не говорят иначе:
эталон — `heuristic-1`, бот на один ход вперёд, не знающий текста большинства
карт. Пригодным это мнение делает читаемость: рядом с каждым разрывом стоят
слагаемые обоих ходов, так что несогласный видит, какой именно вес оспаривать.

Два числа мнением не являются и стоят первыми: шанс, что бросок пройдёт (кубик
против напечатанной сложности), и убьёт ли промах (хиты атакующего против атаки
монстра). «Атаковал Mega Satan при 2 HP на броске 50%» — арифметика; было ли
это неправильно — нет.

Три оговорки:

- **вынужденный ход не решение.** Если движок предложил одно, отчёт не ставит
  это игроку в вину; такие ходы считаются отдельно;
- **место, которое играл сам бот, имеет разрыв ноль по построению** — он не
  может не согласиться с собой. Отчёт называет такие места, чтобы стена нулей
  не читалась как хорошая игра;
- **один и тот же ход, сделанный девять раз, — одна находка.** Строки
  схлопываются с счётчиком «и ещё N раз», иначе три строки отчёта заняла бы
  одна и та же ошибка.

Считается и то, что взвесить не удалось: ответы на вопросы движка мнения бота
не имеют. В разобранной партии — 362 хода взвешено, 20 из них вынужденные, 71
пропущен.

### Замкнутый цикл study → test-card → вердикт

`study` теперь заканчивается разделом **«Worth testing next»**: карты, которые
выделило названное правило, каждая с командой, которая проверила бы догадку.
Печать команды — не удобство, а признание раздела в том, что его собственные
числа ответом не являются.

`fsme test-card --from-study <study.json>` берёт подозреваемых и прогоняет их
по очереди, а `compare` получил однострочный **вердикт**: «эффект в N из M
измерений», «эффекта, различимого этим прогоном, нет» или «слишком редка, чтобы
судить». Формулировка выбрана так, чтобы «эффект не найден» нельзя было
прочитать как «эффекта нет».

**Правило подозреваемых пришлось переписать до того, как оно уехало.** Первая
версия сравнивала долю побед пользователей карты с долей побед по столу и
пометила восемнадцать карт из шестидесяти партий — то есть почти всё, что
использовалось часто. Причина не тонкая: **выигрывающий делает больше ходов, а
значит использует больше карт**, поэтому в пользователях любой карты
непропорционально много победителей. Плюс к этому — множественные сравнения:
порог «две сигмы», приложенный к каждой из сотен карт, пометит десяток и в
идеально сбалансированной колоде.

Обе поправки — простая арифметика, которую можно проверить:

1. места сортируются по числу использованных карт и режутся на полосы (места с
   **одинаковым** числом карт никогда не расходятся по разным полосам —
   иначе поправка вносит обратно тот же перекос); ожидание для карты — сумма
   долей побед по полосам её пользователей, разброс — пуассон-биномиальный;
2. порог отодвигается по числу рассмотренных карт так, чтобы ложная строка
   появлялась в 5% прогонов **на весь отчёт**, а не на карту.

После поправки на тех же 120 партиях по доле побед не проходит **ни одна**
карта, и остаются только строки от правила пар. Это и есть честный ответ: на
таком объёме и с такой поправкой ни одна карта в контенте не измеримо сильна.


# 14. От инструмента разработчика к законченной вещи

Не новые механики и не новые измерения. Четыре шага, после которых проектом
можно пользоваться, не зная его команд.

## 14.1 Один вход — один результат (`fsme report`)

`analysis/party.py` собирает всё, что слой умеет сказать про одну партию, в
порядке, в котором это читают: кто выиграл и из чего сложились души, стол,
моменты, на которых партия повернулась, чем победитель отличался, что было
против остальных, решения в обе стороны и какие карты сделали работу.

Ключевое: отчёт **составляет** существующие отчёты, а не переписывает их. Если
бы `report` и `explain` разошлись в описании одной партии, один из них был бы
неправ, и узнать какой было бы неоткуда.

Понадобилось два добавления:

- **вклад карт** — каждое событие относится к источнику, который назвал движок,
  со знаком в сторону победителя; монстр, который его ранил, идёт в минус. Это
  запись о том, что сделало работу в **этой** партии, а не оценка карты;
- **второй лучший ход** — `Risky.runner_up`. Без него «хорошее решение» ничего
  не значит: взять лучший ход, когда все ходы одинаковы, решением не является.

**Ошибка формулировки, пойманная на выводе.** Первый вариант помечал каждое
расхождение между победителем и столом плюсом, то есть утверждал, что «больше
— лучше». Победитель показательной партии умирал **чаще** стола. Теперь счётные
строки нейтральны, и отчёт прямо говорит, что мнения о направлении счёта у него
нет; минус остался только у названных ботом издержек хода.

## 14.2 Движок и лаборатория (`fsme.lab`)

`bot`, `simulation`, `analysis` (и добавленный позже `desk`) переехали в
`fsme/lab/`. Всё, что играет в Four Souls, осталось на месте.

Граф зависимостей уже был правильным — ядро никогда не импортировало эти
пакеты, — так что переезд превратил случайность в структуру. Дальше важнее:
`tests/test_architecture.py` **читает импорты** и падает, если модуль ядра
потянется в лабораторию. Оба направления названы:

```
FSME Core   правила, карты, эффекты, события, состояние, стек, runtime,
            журнал, api, web
FSME Lab    bot, simulation, analysis, desk
```

Смысл ровно тот, ради которого это и делалось: отчёт не может стать частью
правил, а измерение — изменить измеряемое. Видеть обе стороны разрешено только
`cli`, который для того и существует.

Журнал остался в ядре: его пишет `api.session` во время живой партии, это
запись самого движка, а не инструмент исследования.

## 14.3 Человеческий вход (`fsme desk`)

Одна страница с четырьмя действиями: сыграть партию, запустить исследование,
проверить карту, открыть отчёт. Плюс список работ с прогрессом и вывод.

Правило, на котором всё держится: **страница запускает те же функции и
показывает тот же текст**, что и командная строка. Кнопка, дающая слегка другой
ответ, создала бы два источника истины, и первое расхождение между ними было бы
неразрешимым. На это есть тест: вывод задания сравнивается со строкой, которую
вернул бы `reviewed(review(...))`.

Desk живёт в лаборатории и **наследует** серверу игры из ядра, а не заменяет
его: страница игры и все её эндпоинты работают как работали. Это же и держит
зависимость в разрешённую сторону.

Долгая работа не происходит внутри запроса: задание запускается, страница
спрашивает, как оно продвигается. Числа из браузера зажимаются в разумные
пределы — лишняя цифра в поле это лёгкая ошибка, а случайно запущенный день
симуляции — тяжёлая.

**Настоящая ошибка, найденная при этом.** Пул процессов использовал `fork` (по
умолчанию в Linux). Desk запускает прогоны из фонового потока, а `fork` из
многопоточного процесса копирует замки, которых некому отпустить — ребёнок
может встать намертво. Теперь стартовый метод — `forkserver`, где он есть, иначе
`spawn`. Цена: около 1.4 с на прогон (60 партий: 10.4 → 11.8 с).

## 14.4 Что нашлось при сборке демонстрации

Прогон для демонстрации уронил три партии из четырёхсот — ровно то, ради чего
такие прогоны и делаются.

**`transfer_coins` падал, когда красть не у кого.** Forever Alone говорит
«украдите 1¢ у другого игрока»; в партии на двоих, где второй мёртв, ссылка
`player_of: robbed` не называет никого. Исправлено так же, как раньше
`give_treasure`: инструкция, которую нельзя выполнить, пропускается. Цена
названа в докстринге — способность, автор которой просто забыл указать
источник, теперь молча ничего не делает вместо ошибки; эта проверка всё равно
срабатывала только в рантайме и только в той партии, которая дошла до карты.

**Два зацикливания: Placebo × Rainbow Tapeworm.** Rainbow Tapeworm становится
копией предмета, Placebo копирует способность предмета — и они начинают
копировать друг друга без конца. Правила о бесконечных циклах в спецификациях
**нет**, поэтому правило не выдумывалось: это записано как пробел (§11.5).

Что сделано вместо — движок теперь говорит, **что** зациклилось:

```
game state did not stabilise within 512 steps. Still arriving when it gave up:
stack_push(Placebo) ×10, stack_resolve(Rainbow Tapeworm) ×10, …
```

Последние 60 шагов запоминаются только в хвосте счётчика, так что партия,
которая стабилизировалась (то есть любая нормальная), не платит за это ничего.

**И одна регрессия, которую я внёс сам и поймал через двадцать минут.** Смена
стартового метода процессов на `forkserver` (см. 14.3) ломает запуск лаборатории
из REPL, ноутбука или скрипта, поданного в `python` на stdin: и `forkserver`, и
`spawn` переимпортируют `__main__` в ребёнке, а у такого `__main__` нет файла.
Это нормальный способ пользоваться лабораторией. Теперь метод выбирается в
момент форка по `threading.active_count()`: один поток — `fork`, как и было,
без потери 1.4 с; есть другие потоки (то есть desk) — безопасный метод.

## 14.5 Демонстрация (`docs/DEMONSTRATION.md`)

Документ **генерируется** (`tools/make_demonstration.py`): скрипт играет партии,
запускает команды и вставляет их настоящий вывод, так что любую цифру можно
перепроверить той же командой. Партия лежит в `demo/party.json` и
воспроизводится — `fsme replay` сверяет отпечаток позиции после каждой команды,
поэтому документ является свидетельством, а не утверждением.

Порядок такой: партия сыграна → переиграна и сошлась → полный отчёт → что
говорят сто двадцать партий → карта под тестом. Смысл не в том, что FSME играет
в Four Souls, а в том, что ему можно **задать вопрос** о сыгранной партии и
получить ответ из его собственной записи.


# 15. Аудит пути пользователя

Главный вопрос этапа: **может ли человек, не участвовавший в разработке,
понять ценность FSME и воспользоваться им?** Аудит проводился не по коду, а
руками: чистый venv, `pip install .`, и дальше то, что напечатал бы новичок.

## 15.1 Два блокера: чистая установка вообще не работала

**Карты не попадали в пакет.** `package-data` вёз только `web/static/*.html`.
После `pip install .` команда `fsme` умела печатать свою версию и больше
ничего: движок карточной игры без карт. Данные лежат в `content/` в корне
репозитория — вне `src/`, куда setuptools не смотрит.

Перенести `content/` под `src/fsme/` значило бы починить сборку и испортить то,
ради чего каталог существует: `content/` наверху чекаута — это место, куда
смотрит человек, пишущий карту. Поэтому копирует **сборка** (`setup.py`,
`build_py`): каталог остаётся там, где его ждёт автор, а в колесо попадает
`fsme/carddata/`. Первое же имя (`fsme/cards/`) столкнулось с существующим
пакетом — поймано установкой, а не рассуждением.

**Страница desk тоже не паковалась**, и не значилась в `hiddenimports`
PyInstaller (лаборатория импортируется внутри функций, статически на неё никто
не ссылается). То есть `fsme` без аргументов — путь двойного клика — отдавал
500 и в колесе, и в `.exe`.

## 15.2 Настоящая ошибка в статистике, которую нашёл сам демо-прогон

`fsme demo` прогоняет тест карты на 40 партиях. Он объявил «эффект есть,
+6.58 хода ± 2.48», тогда как тот же тест на 200 партиях давал −2.95 ± 1.09.
Два взаимоисключающих утверждения, оба «за пределами двух сигм», на вложенных
выборках — значит, неверны интервалы, а не карта.

Причина: `_mean` считала дисперсию счётчика равной его среднему — как у
пуассоновского счётчика. Длительность партии не такова: 40–250 ходов при
среднем ~120, то есть настоящий разброс в несколько раз больше. **Интервалы
были примерно в семь раз уже правды**, и тест карты — главный инструмент
проекта — регулярно объявлял эффекты там, где их нет.

Исправлено: `Tally` теперь копит суммы квадратов (`turns_squared` и т.д.),
интервал считается по фактическому разбросу. Суммы складываются между
процессами так же, как всё остальное, — на это есть тест. После исправления:

| Прогон | Было | Стало |
|---|---|---|
| 40 партий | +6.58 ± 2.48 «эффект» | +6.58 ± 18.47 «эффекта не видно» |
| 200 партий | −2.95 ± 1.09 «эффект» | −2.95 ± 7.87 «эффекта не видно» |

Оба «эффекта» были артефактами. Честный интервал, который молчит, лучше узкого,
который говорит неправду.

## 15.3 Где терялся пользователь

| Что было | Что стало |
|---|---|
| `fsme --help` — плоский список из 11 команд в порядке написания | Сгруппирован по задачам, «Start here» первым; тест сверяет группировку с парсером |
| Нет очевидной точки входа | `fsme demo` — минута, без флагов: партия → проверка воспроизводимости → отчёт → тест карты, с печатью команды на каждом шаге |
| Ошибка контента — 20 строк traceback | Отчёт валидатора и строка «что делать»; traceback не показывается |
| «unknown effect 'gain_coinz'» без подсказки | «— did you mean 'gain_coins'?»; порог высокий: неверная подсказка хуже её отсутствия |
| «cannot find the card content» без объяснения | Что это, почему не нашлось, и команда, которая чинит |
| Каталог с набором вне четырёх известных имён **молча игнорировался** | Каталог с манифестом — это набор, где бы он ни лежал |

Последнее — худшая из находок: человек, собравший свой каталог контента,
получал молчание вместо карт. Правило, которое тихо теряет контент, хуже
строгого: автору нечего прочитать.
